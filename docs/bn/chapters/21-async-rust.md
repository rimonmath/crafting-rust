# ২১. অ্যাসিঙ্ক রাস্ট (Async Rust)

## আপনি যা শিখবেন
- **অ্যাসিঙ্ক্রোনাস প্রোগ্রামিং (Asynchronous Programming)** কী এবং ওএস মাল্টি-থ্রেডিংয়ের সাথে এর পার্থক্য কোথায়।
- কীভাবে রাস্ট পোল-ভিত্তিক (poll-based) স্টেট মেশিনের মাধ্যমে **জিরো-কস্ট ফিউচারস (Zero-Cost Futures)** অর্জন করে।
- **`Future`** ট্রেইটের অন্তর্নিহিত গঠন (`poll`, `Pin`, `Context`, এবং `Poll`)।
- কেন রাস্টের স্ট্যান্ডার্ড লাইব্রেরিতে কোনো অ্যাসিঙ্ক রানটাইম নেই এবং কেন **টোকিও (Tokio)** কমিউনিটির প্রধান আর্কিটেকচার।
- **`async fn`** দিয়ে অ্যাসিঙ্ক ফাংশন লেখা এবং **`.await`** অপারেটরের মাধ্যমে নন-ব্লকিং পদ্ধতিতে ফল গ্রহণ।
- **`tokio::join!`** ব্যবহার করে সমান্তরালে একাধিক ফিউচার একযোগে চালানো।
- **`tokio::spawn`** ব্যবহার করে শত শত লাইটওয়েট গ্রিন টাস্ক (Green Tasks) চালানো।
- **`tokio::sync::mpsc`** ব্যবহার করে অ্যাসিঙ্ক মেসেজ চ্যানেল পরিচালনা।
- অ্যাসিঙ্ক রাস্টের সাধারণ ভুল এবং সেগুলো এড়ানোর উপায়:
  - সিনক্রোনাস স্লিপ দিয়ে রানটাইম ব্লক করা (`std::thread::sleep` বনাম `tokio::time::sleep`)।
  - `.await` করতে ভুলে যাওয়া (লেজি ফিউচার ফাঁদ)।
  - `.await`-এর ভেতর সাধারণ সিঙ্ক `MutexGuard` ধরে রাখা।
- মিনিস্টোরে বাস্তব অ্যাসিঙ্ক আর্কিটেকচার তৈরি:
  - `MockPaymentClient` দিয়ে নন-ব্লকিং পেমেন্ট প্রসেসিং।
  - `WarehouseClient` ও `tokio::join!` দিয়ে একাধিক ওয়্যারহাউস থেকে একযোগে রিমোট স্টক যাচাই।
  - `AsyncNotificationBus` দিয়ে ব্যাকগ্রাউন্ড ইভেন্ট বাস।
  - সম্পূর্ণ ট্রানজ্যাকশনাল `async_checkout` প্রসেস।

## আমাদের এটি কেন প্রয়োজন?

২০তম অধ্যায়ে আমরা ওএস থ্রেড (`std::thread::spawn`) দিয়ে সমান্তরাল কাজ সম্পাদন করতে শিখেছি। ওএস থ্রেডগুলো **CPU-বাউন্ড কাজের** জন্য (যেমন অডিও/ভিডিও রেন্ডারিং, এনক্রিপশন, ভারী গাণিতিক হিসাব) দুর্দান্ত। কিন্তু **I/O-বাউন্ড কাজের** ক্ষেত্রে ওএস থ্রেড অত্যন্ত ধীর ও অপচয়মূলক।

### I/O-বাউন্ড জটিলতা
মিনিস্টোরের মতো আধুনিক ই-কমার্স অ্যাপ্লিকেশনের বেশিরভাগ সময়ই কাটে নেটওয়ার্ক বা ডিস্ক থেকে উত্তরের অপেক্ষায়:
- পেমেন্ট গেটওয়ের উত্তরের জন্য অপেক্ষা করা।
- ওয়্যারহাউসের এপিআই বা ইনভেন্টরি ডাটাবেসের জন্য অপেক্ষা করা।
- শিপিং কুরিয়ার ট্র্যাকিং সার্ভিসের জন্য অপেক্ষা করা।

প্রতিটি অপেক্ষারত রিকোয়েস্টের জন্য যদি আপনি একটি করে ওএস থ্রেড চালু করেন:
1. **বিশাল মেমরি অপচয়**: প্রতিটি ওএস থ্রেডের নিজস্ব স্ট্যাক মেমরি থাকে (সাধারণত প্রায় ২ মেগাবাইট)। ১০,০০০ অলস থ্রেড চালু রাখলে কোনো কাজ ছাড়াই প্রায় ২০ গিগাবাইট র‍্যাম নষ্ট হবে!
2. **কনটেক্সট সুইচিং জট**: অপারেটিং সিস্টেমের কার্নেলকে প্রতি সেকেন্ডে হাজার হাজার থ্রেডের মাঝে সিপিইউ অদলবদল (Context Switching) করতে গিয়ে পুরো সিস্টেম ধীর হয়ে পড়ে।

```
ওএস থ্রেড মডেল (ভারী ও প্রিম্পটিভ):
থ্রেড ১ (২ মেগাবাইট) ────► [পেমেন্ট গেটওয়ের অপেক্ষায়...] (অলস)
থ্রেড ২ (২ মেগাবাইট) ────► [ওয়্যারহাউসের অপেক্ষায়...] (অলস)
থ্রেড ৩ (২ মেগাবাইট) ────► [ডাটাবেসের অপেক্ষায়...] (অলস)
```

### অ্যাসিঙ্ক সমাধান: সমবায়ভিত্তিক গ্রিন টাস্ক
প্রতিটি কাজের জন্য আলাদা ভারী ওএস থ্রেড না বানিয়ে **অ্যাসিঙ্ক্রোনাস প্রোগ্রামিং** ব্যবহার করে সমবায়ভিত্তিক বহুমুখী কাজ (Cooperative Multitasking):
- একটি মাত্র ওএস থ্রেডই একসাথে হাজার হাজার অপেক্ষারত কাজ পরিচালনা করতে পারে।
- যখন কোনো কাজ নেটওয়ার্ক থেকে উত্তরের অপেক্ষায় থাকে, তখন সে স্বেচ্ছায় সিপিইউ ছেড়ে দেয় যাতে অন্য কাজগুলো চলতে পারে।
- নেটওয়ার্ক থেকে উত্তর আসা মাত্র রানটাইম সেই স্থগিত কাজটিকে আবার জাগিয়ে তোলে।

```
অ্যাসিঙ্ক রানটাইম মডেল (হালকা ও কোঅপারেটিভ):
একক ওএস থ্রেড ──► [টাস্ক ১: কার্ট চেক] ──► [টাস্ক ২: ইমেইল সেন্ড] ──► [টাস্ক ১: পেমেন্ট সফল!]
প্রতিটি টাস্কের মেমরি সাইজ মাত্র কয়েক শত বাইট, মেগাবাইট নয়!
```

## রাস্টে অ্যাসিঙ্কের গঠন ও মূলনীতি

জাভাস্ক্রিপ্ট (Promises) বা গো (Goroutines)-এর তুলনায় রাস্টের অ্যাসিঙ্ক মডেল সম্পূর্ণ অনন্য।

### ১. ফিউচারস হলো অলস (Futures are Lazy)
জাভাস্ক্রিপ্টে একটি প্রমিজ তৈরি করার সাথে সাথেই ব্যাকগ্রাউন্ডে কাজ শুরু হয়ে যায়। কিন্তু রাস্টে:
> **যতক্ষণ পর্যন্ত কোনো ফিউচারকে পোল (poll) বা `.await` করা না হয়, ততক্ষণ এটি এক লাইন কোডও চালায় না!**

যদি আপনি `.await` না দিয়েই কোনো অ্যাসিঙ্ক ফাংশন কল করেন:
```rust
async fn process_payment() -> String {
    String::from("TX-OK")
}

// সতর্কবার্তা: কোড চলেনি! কেবল একটি অলস Future অবজেক্ট ফেরত এসেছে:
let future = process_payment(); 
```
ফিউচার অলস হওয়ার কারণে যতক্ষণ আপনি নিজে এটিকে শিডিউল না করছেন, ততক্ষণ এটি এক ফোঁটাও অতিরিক্ত রিসোর্স নষ্ট করে না (Zero-Cost Abstraction)।

### ২. `Future` ট্রেইট
ব্যাকগ্রাউন্ডে রাস্টের কম্পাইলার প্রতিটি `async fn`-কে একটি অনামা স্টেট মেশিনে রূপান্তর করে যা স্ট্যান্ডার্ড লাইব্রেরির `Future` ট্রেইট ইমপ্লিমেন্ট করে:

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}
```

- রানটাইম যখন `poll` মেথড ডাকে:
  - কাজ শেষ হলে ফেরত আসে `Poll::Ready(result)`।
  - যদি কাজ এখনও নেটওয়ার্কের অপেক্ষায় থাকে, তবে ফেরত আসে `Poll::Pending` এবং রানটাইমের কাছে একটি `Waker` রেজিস্টার করা হয়।

## অ্যাসিঙ্ক রানটাইম: কেন টোকিও (Tokio) প্রয়োজন?

রাস্টের স্ট্যান্ডার্ড লাইব্রেরি ইচ্ছাকৃতভাবেই কেবল মূল সংজ্ঞাগুলো (`Future`, `Poll`, `Pin`) ধারণ করে। এতে কোনো বিল্ট-ইন রানটাইম বা ইভেন্ট লুপ রাখা হয়নি।

এর ফলে একজন ডেভেলপার যেকোনো পরিবেশের উপযোগী রানটাইম বেছে নিতে পারেন (যেমন মাইক্রোকন্ট্রোলারের জন্য অতি ক্ষুদ্র রানটাইম বনাম বড় সার্ভারের জন্য হাই-থ্রুপুট রানটাইম)।

সার্ভার এবং ব্যাকএন্ড জগতে **টোকিও (Tokio)** হলো বিশ্বস্ত ইন্ডাস্ট্রি স্ট্যান্ডার্ড:
- মাল্টি-থ্রেডেড ওয়ার্ক-স্টিলিং (Work-stealing) টাস্ক শিডিউলার।
- নন-ব্লকিং অ্যাসিঙ্ক টাইমার, নেটওয়ার্কিং (`tokio::net`) এবং ফাইল আই/ও (`tokio::fs`)।
- অ্যাসিঙ্ক চ্যানেল ও লকিং মেকানিজম (`tokio::sync`)।

### `Cargo.toml`-এ টোকিও যুক্ত করা
```toml
[dependencies]
tokio = { version = "1", features = ["full"] }
```

### `#[tokio::main]` ম্যাক্রো
আপনার অ্যাপ্লিকেশনের মেইন ফাংশনকে অ্যাসিঙ্ক করতে এর উপরে `#[tokio::main]` বসিয়ে দিন:

```rust
#[tokio::main]
async fn main() {
    println!("টোকিও অ্যাসিঙ্ক রানটাইম সফলভাবে শুরু হয়েছে!");
}
```

## নন-ব্লকিং আই/ও: `async fn` এবং `.await`

রাস্টে অ্যাসিঙ্ক কোড লেখা সাধারণ কোড লেখার মতোই সহজ, কেবল দুটি পরিবর্তন মনে রাখতে হবে:
1. `async fn`: ফাংশনটি সাধারণ মানের বদলে একটি `Future` রিটার্ন করবে।
2. `.await`: ফিউচারটির ফলাফল প্রস্তুত না হওয়া পর্যন্ত বর্তমান টাস্ককে থামিয়ে রাখবে, যাতে সেই ফাঁকে থ্রেড অন্য কাজ করতে পারে।

```rust
use std::time::Duration;
use tokio::time::sleep;

async fn fetch_stock_online(sku: &str) -> u32 {
    // নন-ব্লকিং অ্যাসিঙ্ক স্লিপ (নেটওয়ার্ক লেটেন্সি সিমুলেশন)
    sleep(Duration::from_millis(50)).await;
    
    match sku {
        "TECH-KEY-001" => 15,
        _ => 0,
    }
}
```

> [!WARNING]
> কোনো `async fn`-এর ভেতর ভুলেও `std::thread::sleep` ব্যবহার করবেন না!
> `std::thread::sleep` পুরো অপারেটিং সিস্টেম থ্রেডটিকে জাম করে দেয়, ফলে সেই থ্রেডে থাকা অন্য সব অ্যাসিঙ্ক টাস্ক আটকে যায়। সবসময় `tokio::time::sleep` ব্যবহার করবেন।

## সমান্তরাল ফিউচারস: `tokio::join!`

যদি একসাথে দুটি রিমোট সার্ভার থেকে ডেটা আনতে হয়?

### ধারাবাহিক এক্সিকিউশন (ধীরগতি)
```rust
let stock_a = warehouse_a.check_stock(sku).await?; // ৫০ মিলিসেকেন্ড
let stock_b = warehouse_b.check_stock(sku).await?; // ৫০ মিলিসেকেন্ড
// মোট সময় লাগবে: ১০০ মিলিসেকেন্ড!
```

### `tokio::join!` দিয়ে সমান্তরাল এক্সিকিউশন (দ্রুতগতি)
`tokio::join!` ম্যাক্রো একাধিক ফিউচারকে একই সাথে সমান্তরালে রানটাইমে ছেড়ে দেয়:

```rust
// দুটি রিকোয়েস্ট একসাথেই চালু হবে!
let (res_a, res_b) = tokio::join!(
    warehouse_a.check_stock(sku),
    warehouse_b.check_stock(sku)
);
// মোট সময় লাগবে: মাত্র ~৫০ মিলিসেকেন্ড!
```

মিনিস্টোরের `ministore/src/async_services.rs`-এ আমরা এই প্যাটার্ন ব্যবহার করেছি:
```rust
pub async fn aggregate_warehouse_stock(
    warehouse_a: &WarehouseClient,
    warehouse_b: &WarehouseClient,
    sku: &str,
) -> Result<u32, StoreError> {
    let (res_a, res_b) = tokio::join!(
        warehouse_a.check_stock(sku),
        warehouse_b.check_stock(sku)
    );

    let stock_a = res_a?;
    let stock_b = res_b?;
    Ok(stock_a + stock_b)
}
```

## গ্রিন টাস্ক চালু করা: `tokio::spawn`

`tokio::join!` বর্তমান টাস্কের ভেতরেই একাধিক ফিউচার চালায়, অন্যদিকে `tokio::spawn` ব্যাকগ্রাউন্ডে সম্পূর্ণ স্বাধীন একটি **টোকিও টাস্ক (Green Thread)** শুরু করে:
- টাস্কগুলো টোকিও থ্রেড পুলে স্বাধীনভাবে চলতে থাকে।
- একটি নতুন টাস্ক স্পন করতে ১ মাইক্রোসেকেন্ডেরও কম সময় এবং মাত্র কয়েক শত বাইট মেমরি লাগে।

```rust
let task = tokio::spawn(async move {
    println!("ব্যাকগ্রাউন্ড অডিট বা টেলিমোট্রি চলছে...");
    42
});

let result = task.await.unwrap();
assert_eq!(result, 42);
```

## অ্যাসিঙ্ক মেসেজ চ্যানেল: `tokio::sync::mpsc`

স্ট্যান্ডার্ড লাইব্রেরির চ্যানেলগুলো সিঙ্ক্রোনাস এবং থ্রেড ব্লক করে। টোকিও নিজস্ব নন-ব্লকিং অ্যাসিঙ্ক চ্যানেল প্রদান করে:

```rust
use tokio::sync::mpsc;

// ৩২টি মেসেজের বাফার সাইজসহ চ্যানেল
let (tx, mut rx) = mpsc::channel(32);

tokio::spawn(async move {
    tx.send("Order #901 Completed").await.unwrap();
});

// নন-ব্লকিং গ্রহণ:
if let Some(msg) = rx.recv().await {
    println!("গৃহীত অ্যাসিঙ্ক ইভেন্ট: {msg}");
}
```

মিনিস্টোরে এটি `AsyncNotificationBus`-এ অন্তর্ভুক্ত:
```rust
pub struct AsyncNotificationBus {
    sender: mpsc::Sender<OrderNotification>,
}

impl AsyncNotificationBus {
    pub fn new(buffer: usize) -> (Self, mpsc::Receiver<OrderNotification>) {
        let (sender, receiver) = mpsc::channel(buffer);
        (Self { sender }, receiver)
    }

    pub async fn dispatch(
        &self,
        notification: OrderNotification,
    ) -> Result<(), mpsc::error::SendError<OrderNotification>> {
        self.sender.send(notification).await
    }
}
```

## মিনিস্টোরে অ্যাসিঙ্ক বাস্তবায়ন

এই অধ্যায়ে আমরা মিনিস্টোরে নন-ব্লকিং অ্যাসিঙ্ক সার্ভিস যুক্ত করেছি:

```
ministore/
├── Cargo.toml              # tokio ডিপেন্ডেন্সি সংযুক্ত
├── src/
│   ├── async_services.rs   # MockPaymentClient, WarehouseClient, AsyncNotificationBus, async_checkout
│   ├── concurrency.rs
│   ├── catalog.rs
│   ├── promotions.rs
│   ├── models/
│   ├── lib.rs              # ৪৯টি টেস্ট
│   └── main.rs             # অ্যাসিঙ্ক পেমেন্ট, tokio::join!, এবং async_checkout প্রদর্শন
```

### সম্পূর্ণ ট্রানজ্যাকশনাল `async_checkout`
```rust
pub async fn async_checkout(
    order_id: OrderId,
    customer: Customer,
    cart: &mut ShoppingCart,
    catalog: &mut Catalog,
    payment_method: PaymentMethod,
    coupon: Option<Coupon>,
    payment_client: &MockPaymentClient,
) -> Result<(Order, String), StoreError> {
    // ১. ডোমেইন স্টক যাচাই ও অর্ডার অবজেক্ট গঠন
    let order = crate::checkout::checkout(
        order_id, customer, cart, catalog, payment_method.clone(), coupon
    )?;

    // ২. নন-ব্লকিং অ্যাসিঙ্ক পেমেন্ট প্রসেসিং
    let tx_receipt = payment_client
        .process_payment(&payment_method, order.total_cents())
        .await?;

    Ok((order, tx_receipt))
}
```

## সাধারণ এরর ও সম্ভাব্য জটিলতা

### ১. অলস ফিউচার ফাঁদ (Unused Must-Use)
```rust
payment_client.process_payment(&card, 5000);
// Warning: unused implementor of `Future` that must be used!
```
**সমাধান**: ফাংশনটির শেষে `.await` যুক্ত করে ফলাফল সংগ্রহ করুন:
```rust
payment_client.process_payment(&card, 5000).await?;
```

### ২. `.await`-এর মধ্য দিয়ে `std::sync::MutexGuard` ধরে রাখা
স্ট্যান্ডার্ড `MutexGuard` থ্রেডের মাঝে মুভ হতে পারে না। ফলে কোনো ফিউচার যদি মিউটেক্স ধরে থাকা অবস্থায় ঘুমিয়ে পড়ে (`.await`), তবে অন্য থ্রেড সেই ফিউচার চালাতে পারবে না এবং কম্পাইলার এরর দেবে।
**সমাধান**:
- লকের স্কোপ কার্লি ব্র্যাকেট `{ ... }` দিয়ে সীমাবদ্ধ রাখুন যাতে `.await`-এর আগেই তালা খুলে যায়।
- অথবা প্রয়োজনবোধে `tokio::sync::Mutex` ব্যবহার করুন।

## অনুশীলনী (Hands-On Exercises)

1. **অ্যাসিঙ্ক টাইমআউট গার্ড**:
   `tokio::time::timeout` পরীক্ষা করুন। `payment_client.process_payment` কলে ৩০ মিলিসেকেন্ডের টাইমআউট দিয়ে ১০০ মিলিসেকেন্ড লেটেন্সি পাঠিয়ে দেখুন যে এটি সফলভাবে এরর প্রদান করছে কি না।
2. **`tokio::select!` দিয়ে ফার্স্ট-রেসপন্ডার প্যাটার্ন**:
   দুটি ওয়্যারহাউসে একসাথে রিকোয়েস্ট পাঠিয়ে যে ওয়্যারহাউস সবার আগে উত্তর দেবে তার স্টক গ্রহণ করার কোড লিখুন।
3. **টাস্ক বাতিল করা (Cancellation)**:
   `tokio::spawn` দিয়ে একটি অবিরাম লুপের টাস্ক চালান এবং `task.abort()` দিয়ে সেটিকে মাঝপথে বাতিল করে দেখুন।

## অধ্যায় সারসংক্ষেপ ও অ্যাসিঙ্ক চিটশিট

| উপাদান | উৎস | মূল কাজ | ওভারহেড |
| :--- | :--- | :--- | :--- |
| **`async fn`** | মূল রাস্ট ভাষা | অলস ফিউচার স্টেট মেশিন ঘোষণা | শূন্য (Zero Cost) |
| **`.await`** | মূল রাস্ট ভাষা | ফলাফল প্রস্তুত হওয়া পর্যন্ত বিরতি | ন্যূনতম |
| **`tokio::main`** | টোকিও ম্যাক্রো | মাল্টি-থ্রেডেড অ্যাসিঙ্ক রানটাইম শুরু | অ্যাপ প্রতি একটি |
| **`tokio::join!`** | টোকিও ম্যাক্রো | সমান্তরালে একাধিক ফিউচার চালানো | একক টাস্ক |
| **`tokio::spawn`** | টোকিও ফাংশন | ব্যাকগ্রাউন্ড গ্রিন টাস্ক চালু | কয়েক শত বাইট |
| **`tokio::time::sleep`** | টোকিও ফাংশন | নন-ব্লকিং টাইমার বিরতি | টাইমার হুইল এন্ট্রি |
| **`tokio::sync::mpsc`** | টোকিও চ্যানেল | অ্যাসিঙ্ক বার্তা আদান-প্রদান | রিং বাফার |

পরবর্তী অধ্যায়ে আমরা ইন-মেমরি থেকে **অ্যাপ্লিকেশন লেয়ারে (Application Layer)** প্রবেশ করব, যেখানে শিখব **পারসিস্টেন্স (Persistence)**—ফাইল আই/ও এবং সার্ডে (Serde) দিয়ে JSON সিরিয়ালাইজেশন!
