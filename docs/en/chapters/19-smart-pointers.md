## Why Do We Need This?

In previous chapters, we mastered Rust's strict compile-time ownership and borrowing model:
1. **Every value has exactly one owner.**
2. **You can have any number of immutable references (`&T`), OR exactly one mutable reference (`&mut T`), but never both at the same time.**
3. **Rust must know the exact memory size of every variable at compile time.**

While these guarantees deliver absolute memory safety without a garbage collector, real-world application architectures encounter scenarios where standard stack values and references alone become restrictive:

### Scenario 1: Heterogeneous Collections of Closures
In Chapter 18, we discovered that every closure has a distinct, unnameable type generated by the compiler. When we wanted to store multiple discount rules in a single collection (`Vec<F>`), the compiler forced every closure in the vector to have the exact same type:
```rust
// In Chapter 18:
let rule_pct = make_percentage_discount(10);
let rule_thresh = make_threshold_discount(10000, 1500);

// COMPILER ERROR! rule_pct and rule_thresh have different anonymous types:
// let rules = vec![rule_pct, rule_thresh];
```
How can we store a dynamic list of mixed discount strategies in a single pipeline?

### Scenario 2: Recursive Data Structures
Suppose our e-commerce store needs a category tree: an "Electronics" category containing subcategories like "Computers", which in turn contains "Laptops". If a struct directly contains child instances of itself, its size would be infinite:
```rust
// COMPILER ERROR: recursive type has infinite size
struct CategoryNode {
    name: String,
    subcategories: Vec<CategoryNode>, // Without indirection, how does Rust allocate this?
}
```

### Scenario 3: Shared Read-Only Ownership
Suppose multiple parts of our application (an active shopping cart, a checkout transaction, and an audit logger) all need to hold an owned handle to the same `Customer` profile. Cloning the entire `Customer` struct every time duplicates heap memory (`String`, `HashSet`, etc.). We need multiple owners pointing to the *same* heap allocation.

### Scenario 4: Shared Mutable State
Suppose multiple promotion evaluation passes need to update a single shared discount auditor. Because Rust prevents aliased mutation, how can two independent handles mutate the same shared accounting tracker in a single-threaded program?

Smart pointers solve every single one of these challenges.

## What is a Smart Pointer?

In systems programming, a **pointer** is a variable that stores the memory address of another value. In Rust, standard references (`&T` and `&mut T`) are non-owning pointers that borrow data without overhead.

A **Smart Pointer** is a data structure that acts like a pointer, but also possesses additional metadata, capabilities, and ownership semantics. Crucially, smart pointers usually **own** the data they point to.

Rust's standard library smart pointers rely on two fundamental traits from `std::ops`:
- **`Deref`** (and `DerefMut`): Allows instances of the smart pointer to behave like references, enabling the dereference operator (`*ptr`) and transparent method calls via **deref coercion**.
- **`Drop`**: Allows customizing the code that executes when the smart pointer leaves scope, ensuring automatic, deterministic memory and resource cleanup (RAII).

| Type | Allocation | Ownership | Mutability Enforcement | Common Use Case |
| :--- | :--- | :--- | :--- | :--- |
| `&T` | Borrows (stack or heap) | Non-owning borrow | Compile-time (immutable) | Temporary zero-cost access |
| `&mut T` | Borrows (stack or heap) | Non-owning borrow | Compile-time (exclusive mutable) | Temporary exclusive mutation |
| `Box<T>` | Heap | Single owner | Compile-time | Known size, recursion, trait objects |
| `Rc<T>` | Heap | Multiple owners (ref-counted) | Compile-time (immutable) | Shared read access in single-thread |
| `RefCell<T>` | Stack or Heap | Single owner | **Runtime** (interior mutability) | Mutating behind immutable `&T` |
| `Rc<RefCell<T>>` | Heap | Multiple owners | **Runtime** | Shared mutable state in single-thread |

## `Box<T>`: Heap Allocation & Dynamic Sizing

`Box<T>` is the simplest smart pointer. It allocates data on the heap while keeping a fixed-size pointer (one usize: 8 bytes on a 64-bit architecture) on the stack. When the `Box` goes out of scope, both the stack pointer and the heap-allocated payload are deallocated.

```rust
// Primitive 42 is stored on the heap; `boxed_val` lives on the stack
let boxed_val: Box<u32> = Box::new(42);
assert_eq!(*boxed_val, 42); // Dereferencing accesses the heap value
```

### 1. Recursive Data Structures with `Box<T>`
Rust must know how much memory to allocate for every type at compile time. Recursive types (types that contain values of the same type as fields) cannot have their size determined directly because their depth could be indefinite.

By wrapping recursive fields in `Box<T>`, we introduce a level of indirection: the struct now contains a pointer of known, fixed size on the stack, while the recursive child lives on the heap:

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct CategoryNode {
    pub name: String,
    pub subcategories: Vec<Box<CategoryNode>>,
}

impl CategoryNode {
    pub fn new(name: impl Into<String>) -> Self {
        Self {
            name: name.into(),
            subcategories: Vec::new(),
        }
    }

    pub fn add_subcategory(&mut self, child: CategoryNode) {
        self.subcategories.push(Box::new(child));
    }

    pub fn total_categories(&self) -> usize {
        1 + self.subcategories.iter().map(|s| s.total_categories()).sum::<usize>()
    }
}
```

```
Stack: CategoryNode ("Electronics")
  ├── name: "Electronics"
  └── subcategories: Vec<Box<CategoryNode>>
                             │
                             ▼ (Heap)
                    CategoryNode ("Computers")
                      └── subcategories: Vec<Box<CategoryNode>>
                                                 │
                                                 ▼ (Heap)
                                        CategoryNode ("Laptops")
```

### 2. Trait Objects & Dynamic Dispatch (`Box<dyn Trait>`)
In Chapter 18, we saw that every closure has a unique compiler-generated type. To store different closures in a single `Vec`, we must use a **trait object** (`dyn Trait`) wrapped in `Box`:

```rust
// Trait object: Box<dyn Fn(u32) -> u32>
pub type BoxedDiscount = Box<dyn Fn(u32) -> u32>;

pub struct PromotionPipeline {
    rules: Vec<BoxedDiscount>,
}

impl PromotionPipeline {
    pub fn new() -> Self {
        Self { rules: Vec::new() }
    }

    pub fn add_rule<F>(&mut self, rule: F)
    where
        F: Fn(u32) -> u32 + 'static,
    {
        self.rules.push(Box::new(rule));
    }

    pub fn apply_all(&self, amount_cents: u32) -> u32 {
        self.rules.iter().map(|rule| rule(amount_cents)).sum()
    }
}
```

Now, we can add a percentage discount closure AND a threshold discount closure into the exact same pipeline:
```rust
let mut pipeline = PromotionPipeline::new();
pipeline.add_rule(make_percentage_discount(10));
pipeline.add_rule(make_threshold_discount(15000, 2000));

// Works seamlessly! Both closures are boxed as trait objects on the heap.
assert_eq!(pipeline.apply_all(20000), 4000);
```

## The `Deref` Trait & Deref Coercion

The `Deref` trait from `std::ops` enables customizing the behavior of the dereference operator (`*`).

```rust
pub trait Deref {
    type Target: ?Sized;
    fn deref(&self) -> &Self::Target;
}
```

When you write `*my_box`, Rust behind the scenes translates it into:
```rust
*(my_box.deref())
```

### Deref Coercion
Rust provides **Deref Coercion**: an automatic, compile-time convenience that converts a reference to a type implementing `Deref` into a reference to its target type (`&MyPointer<T>` becomes `&T`).

For example, `String` implements `Deref<Target = str>`. Therefore, a function accepting `&str` will automatically accept `&String` without needing explicit syntax.

### Custom Smart Pointer: `StoreSession<T>`
Let's see how `Deref` and `DerefMut` empower our custom `StoreSession<T>` wrapper:

```rust
use std::ops::{Deref, DerefMut};

#[derive(Debug, PartialEq, Eq)]
pub struct StoreSession<T> {
    pub session_id: String,
    pub inner: T,
}

impl<T> Deref for StoreSession<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        &self.inner
    }
}

impl<T> DerefMut for StoreSession<T> {
    fn deref_mut(&mut self) -> &mut Self::Target {
        &mut self.inner
    }
}
```

Because `StoreSession<Customer>` implements `Deref<Target = Customer>`, you can call any method defined on `Customer` directly on the session:
```rust
let mut session = StoreSession::new("SESS-01", customer);

// Deref coercion: Customer::display_badge() called directly on StoreSession!
println!("{}", session.display_badge());

// DerefMut: Customer::upgrade_to_vip() mutates inner customer through session!
session.upgrade_to_vip();
```

## The `Drop` Trait: Deterministic Cleanup

In languages like C, developers must remember to call `free()` for every heap allocation. In garbage-collected languages like JavaScript, memory cleanup happens nondeterministically during GC sweeps.

Rust uses **RAII** (Resource Acquisition Is Initialization). When an owner goes out of scope, Rust automatically calls the `drop` method of the `Drop` trait:

```rust
pub trait Drop {
    fn drop(&mut self);
}
```

### Implementing `Drop` on `StoreSession<T>`
```rust
use std::cell::RefCell;
use std::rc::Rc;

pub struct StoreSession<T> {
    pub session_id: String,
    pub inner: T,
    drop_flag: Option<Rc<RefCell<bool>>>,
}

impl<T> Drop for StoreSession<T> {
    fn drop(&mut self) {
        println!("Cleaning up session [{}]...", self.session_id);
        if let Some(ref flag) = self.drop_flag {
            *flag.borrow_mut() = false; // Mark session inactive
        }
    }
}
```

```rust
let active_flag = Rc::new(RefCell::new(false));
{
    let session = StoreSession::with_drop_flag("SESS-01", customer, Rc::clone(&active_flag));
    assert!(*active_flag.borrow()); // Session is active
} // <-- session goes out of scope here; Drop::drop executes automatically!

assert!(!*active_flag.borrow()); // Verified: session deactivated upon exit!
```

> [!NOTE]
> If you need to drop a value early before its enclosing scope ends, you cannot call `session.drop()` directly (the compiler prevents this to avoid double-free errors). Instead, call `std::mem::drop(session)`.

## `Rc<T>`: Reference Counting & Multiple Ownership

Standard Rust ownership is strictly 1:1. However, in graph structures, event subscribers, or shared domain sessions, a single value might have multiple owners.

`Rc<T>` stands for **Reference Counted**. It provides shared read-only ownership of a value allocated on the heap:

```rust
use std::rc::Rc;

let customer = Rc::new(Customer::new(
    301,
    String::from("Margaret Hamilton"),
    String::from("margaret@apollo.nasa.gov"),
    None,
    true,
));

// Strong count is 1
assert_eq!(Rc::strong_count(&customer), 1);

// Clone only duplicates the pointer and increments the counter (shallow copy)
let session_ref = Rc::clone(&customer);
let audit_ref = Rc::clone(&customer);

// Strong count is now 3
assert_eq!(Rc::strong_count(&customer), 3);

// Both handles read the exact same heap memory:
assert_eq!(session_ref.name, "Margaret Hamilton");
assert_eq!(audit_ref.name, "Margaret Hamilton");

// Dropping one handle decrements the strong count:
drop(audit_ref);
assert_eq!(Rc::strong_count(&customer), 2);
```

```
               ┌─────────────┐
session_ref ──►│             │
               │   Heap:     │
customer ─────►│ Customer    │  (Strong Count: 2)
               │             │
               └─────────────┘
```

> [!IMPORTANT]
> `Rc<T>` is strictly for **single-threaded** execution. If you try to send an `Rc<T>` across thread boundaries, the Rust compiler will reject it because `Rc<T>` does not implement the `Send` or `Sync` traits. Multi-threaded atomic reference counting (`Arc<T>`) is covered in Chapter 20 (Concurrency).

## `RefCell<T>` and the Interior Mutability Pattern

`Rc<T>` gives multiple owners, but **only allows immutable access (`&T`)**. What if multiple owners need to share a data structure and mutate it?

Under standard Rust rules, mutating data requires an `&mut T` reference, which prevents any other references from existing.

**Interior Mutability** is a design pattern in Rust that allows you to mutate data even when you have an immutable reference (`&T`) to that data. To achieve this, the data structure uses `unsafe` code inside its internal abstraction while presenting a completely safe, verified interface to callers.

`RefCell<T>` implements this pattern by moving borrowing rule enforcement from **compile time** to **runtime**:

| Rule | Compile Time (`&T` / `&mut T`) | Runtime (`RefCell<T>`) |
| :--- | :--- | :--- |
| **Immutable borrows** | `&T` (unlimited) | `.borrow()` -> `Ref<T>` (unlimited) |
| **Mutable borrows** | `&mut T` (exactly 1) | `.borrow_mut()` -> `RefMut<T>` (exactly 1) |
| **Rule Violation** | Compilation Error | **Runtime Panic** (`already borrowed`) |

### Example: Basic `RefCell<T>`
```rust
use std::cell::RefCell;

let cell = RefCell::new(100);

// Mutating through an immutable reference!
{
    let mut mut_borrow = cell.borrow_mut();
    *mut_borrow += 50;
} // RefMut goes out of scope here

// Reading through an immutable borrow:
assert_eq!(*cell.borrow(), 150);
```

### The Runtime Panic Catch
If you attempt to call `.borrow_mut()` while an active borrow is still alive in the same scope:
```rust
let cell = RefCell::new(42);

let b1 = cell.borrow();
let mut b2 = cell.borrow_mut(); // PANIC: already borrowed: BorrowMutError!
```
To avoid panicking in production, you can use `.try_borrow()` and `.try_borrow_mut()`, which return a `Result`.

## Combining `Rc<T>` and `RefCell<T>`

By combining `Rc<T>` with `RefCell<T>`, we achieve the holy grail of single-threaded programming: **multiple owners with shared mutable access!**

```
              ┌──────────────────────────┐
handle_a ────►│   Rc (Strong Count: 2)   │
              │             │            │
handle_b ────►│             ▼            │
              │    RefCell<DiscountAuditor>
              │    (Runtime borrow checked)
              └──────────────────────────┘
```

### MiniStore Implementation: `SharedAuditor`
In `ministore/src/promotions.rs`, we define `SharedAuditor`:

```rust
use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug, Clone, Default)]
pub struct SharedAuditor {
    inner: Rc<RefCell<DiscountAuditor>>,
}

impl SharedAuditor {
    pub fn new() -> Self {
        Self {
            inner: Rc::new(RefCell::new(DiscountAuditor::new())),
        }
    }

    /// Records a discount using interior mutability via `borrow_mut()`.
    /// Note: This method takes `&self` (immutable reference), yet mutates internal state!
    pub fn record(&self, discount_cents: u32) {
        self.inner.borrow_mut().record(discount_cents);
    }

    pub fn total_discount_given(&self) -> u32 {
        self.inner.borrow().total_discount_given
    }

    pub fn operations_count(&self) -> u32 {
        self.inner.borrow().operations_count
    }

    pub fn strong_count(&self) -> usize {
        Rc::strong_count(&self.inner)
    }
}
```

```rust
let auditor1 = SharedAuditor::new();
let auditor2 = auditor1.clone(); // Second owner pointing to the same ledger

// Record via auditor2 through immutable &auditor2
auditor2.record(1500);

// Both handles immediately observe the updated accounting:
assert_eq!(auditor1.operations_count(), 1);
assert_eq!(auditor1.total_discount_given(), 1500);
assert_eq!(auditor2.total_discount_given(), 1500);
```

## Common Compiler & Runtime Errors

### 1. `error[E0072]: recursive type has infinite size`
```rust
struct CategoryNode {
    subcategories: Vec<CategoryNode>, // Recursive without Box
}
```
**Why it occurs**: The compiler cannot determine how many bytes to allocate on the stack for a type that contains itself directly.
**Fix**: Introduce a pointer indirection using `Box`:
```rust
struct CategoryNode {
    subcategories: Vec<Box<CategoryNode>>,
}
```

### 2. `error[E0596]: cannot borrow data in an 'Rc' as mutable`
```rust
let customer = Rc::new(Customer::new(...));
customer.upgrade_to_vip(); // Error! Rc only provides immutable &T borrows.
```
**Why it occurs**: `Rc<T>` does not permit mutable borrows of its payload because there are multiple owners.
**Fix**: Wrap the inner payload in `RefCell<T>` (`Rc<RefCell<Customer>>`) to enable interior mutability.

### 3. `already borrowed: BorrowMutError` (Runtime Panic)
```rust
let cell = RefCell::new(vec![1, 2, 3]);
let reader = cell.borrow();
let mut writer = cell.borrow_mut(); // PANIC at runtime!
```
**Why it occurs**: You attempted to acquire a mutable borrow while an active immutable borrow was still in scope.
**Fix**: Limit the lifetime of borrows using explicit curly-brace scopes `{ ... }` or `drop(reader)` before calling `cell.borrow_mut()`.

## Chapter Summary & Pointer Cheatsheet

| Pointer | Definition | When to Use | Memory Overhead |
| :--- | :--- | :--- | :--- |
| **`&T` / `&mut T`** | Standard Rust references | Temporary zero-cost borrowing | None (pointer address only) |
| **`Box<T>`** | Unique owning heap pointer | Known stack size, recursive types, trait objects | 1 pointer on stack + heap data |
| **`Rc<T>`** | Reference counted pointer | Multiple single-threaded read-only owners | 2 usize counters + heap data |
| **`RefCell<T>`** | Interior mutability container | Mutating behind `&T`, runtime borrow check | 1 isize borrow counter |
| **`Rc<RefCell<T>>`** | Shared mutable container | Multiple single-threaded owners that mutate | Counters + heap allocation |
